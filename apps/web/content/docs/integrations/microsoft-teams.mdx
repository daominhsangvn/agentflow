## What it does

One connection has two independent parts, and at least one must be set:

- **Workflows webhook** to post cards to a channel.
- **Bot** (an Azure Bot) to be mentioned in channels and to answer in the thread.

## Connection settings

| Key | Notes |
|---|---|
| secret `webhookUrl` | A Teams Workflows webhook ("Send webhook alerts to a channel"). Old Office 365 connector webhooks are rejected |
| `config.appId`, `config.tenantId` | The Azure Bot (single tenant) |
| secret `clientSecret` | The bot's app registration secret |
| `inbound.mode` | `webhook`: the inbound URL is the Azure Bot's messaging endpoint, so it must be public HTTPS (behind NAT, use a tunnel and `PUBLIC_WEBHOOK_BASE_URL`) |

Project settings:

- `channels` (links or ids) lists where mentioning the bot starts this project's workflows. Empty means the project only posts.
- **Ask channels** (`askChannels`) lists where an Orchestrator Agent may ask people, one entry per channel: `name = <channel link or id>`. The name may be left out for a channel link (the channel's name is used); a bare id needs one. Names are unique per connection. An ask channel is claimed by the project like a mention channel, so a channel another project claims is refused. Keep ask channels out of the `channels` filter of non-orchestrated `bot_mentioned` triggers. Private channels are not supported.

## Asking people (orchestrated workflows)

A workflow that grants the Teams key `ask` (`agent.orchestrator.connections.teams: [ask]`) lets its Orchestrator Agent ask people in an ask channel. The rules choose the channel by name and give the people's emails; the Agent never guesses an email.

```yaml
connections:
  teams: [ask]
instructions: |
  Backend questions go to people in the qa-backend channel; requirement questions in ba.
  Emails: Lan (QA) lan@example.com, Minh (BA) minh@example.com.
```

- **One thread per case and channel.** The first ask of a case opens a new post that @mentions the people; later asks of the same case to the same channel are replies in that thread. A new post is made when the thread's first message is gone or posting in the thread fails.
- **Replies need the bot mention.** A message in the thread that does not @mention the bot is ignored. Anyone in the channel can write; the case records who wrote and whether that person was asked. A reply goes to the newest open ask of the thread that mentions its writer, else to the newest open ask.
- **Nothing is answered until confirmed.** The Orchestrator Agent may discuss in the thread, then posts a summary of the answers. The answers are recorded on the case only when one of the people that ask mentioned confirms that summary in a later message of the thread. A confirmation from anyone else, or one written before the summary, is refused. A confirmation confirms only the newest summary before it.
- A bot mention in a thread with no ask and no matching trigger opens nothing: no reply, no case.

Tools: [`teams_ask`, `teams_ask_reply`, `teams_ask_confirm`](/docs/reference/orchestrator-tools). Rules: [Questions and answers](/docs/guides/recipes/questions-and-answers#asking-people-in-teams).

## Triggers

| Type | Starts when |
|---|---|
| `microsoft_teams.bot_mentioned` | A channel message in the bot's tenant mentions the bot, as a new post or a thread reply. The item is the **thread**: one run per thread, and another mention resumes a run that waits for input. Filter: `channels`. Group chats, personal chats and other tenants are ignored |

A reply in a thread that does not mention the bot (`microsoft_teams.thread_reply`) is not a trigger. Only an Orchestrator Agent that already talks in that thread receives it.

### Several mentions in one thread

By default a mention in a thread that already has an active run does nothing, and a run that waits for input takes the mention as its answer. A workflow can set `agent.sameItem` (see [Workflow YAML](/docs/guides/setup/workflow-yaml)) to change that:

- `queue`: each mention starts its own run. The runs of one thread run one after another, and a run starts only after the previous run's reply is posted (it waits at most 15 minutes for that). Other threads run in parallel. Each reply mentions the person who wrote its own mention.
- `queue_resume`: as `queue`, and the run continues the agent session of the thread's previous run on the same runner, told only what was written in the thread since. If that runner is offline, too old to report a missing session, or no longer has the session, the run starts a new session with the whole thread. A new session is also told which message is this run's request, so it does not answer later messages in the thread.

```yaml
agent:
  sameItem: queue_resume
```

Not available for orchestrated workflows. A failed run of a thread cannot be retried while another run of that thread is open, and with `queue_resume` not after a later run exists; mention the bot again instead.

## Actions

| Operation | What it does |
|---|---|
| `microsoft_teams.post_message` | Posts an Adaptive Card (title, text, facts, buttons) through the webhook |
| `microsoft_teams.reply` | Answers in the thread the run came from, optionally starting with an @mention of the requester. Skipped for runs that did not come from Teams |

## Setup

The connection page shows the setup steps and a Teams app manifest template; the app needs the RSC permission `ChannelMessage.Read.Group`. See [Connections and repositories](/docs/guides/setup/connections).

## Limits

- Anyone in the channel can ask. Thread text is untrusted input, like ticket text.
- Up to 500 replies of a thread are read; the oldest are dropped above 60 000 characters.
