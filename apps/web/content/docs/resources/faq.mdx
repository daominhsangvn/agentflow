## Does AgentFlow need a cloud service?

No. You host the app, API and MCP server yourself. Object storage is RustFS over the S3 protocol, the database is PostgreSQL, and Local Git repositories live on your own disk. See [Install the server](/docs/getting-started/install-server).

## Which models does it use?

Agents run Claude Code. You can point an Agent at an Anthropic-compatible provider with the Model provider setting on the Agent. The Model provider also pins the Claude Code version. See [Agents](/docs/guides/setup/agents).

## Where are credentials stored?

In Connections. Secrets are encrypted at rest with `ENCRYPTION_KEY`. Agents never receive the credentials of a connection: they call the integration through the platform. See [Connections](/docs/guides/setup/connections) and [Connection grants](/docs/guides/setup/connection-grants).

## What is the difference between an automatic and a personal Agent?

An automatic Agent is a long-running process an admin installs on a server or container. It connects out to the API, clones the project's repositories and uses Git credentials issued by AgentFlow; AgentFlow does not start it. A personal Agent runs on a person's own machine with their local credentials. Both appear on the [Agents page](/docs/guides/operate/agents). See [Agents](/docs/guides/setup/agents).

## What is the difference between an orchestrated workflow and a run-based one?

A run-based workflow runs a fixed sequence of steps. An orchestrated workflow follows rules written in plain language: the Orchestrator Agent reads each ticket change or comment and decides what tasks to start. See [Orchestrated vs process workflows](/docs/concepts/orchestrated-vs-process).

## Can people approve work in Jira?

Yes. A person moves the ticket to another status or replies in the comments, and the Orchestrator Agent reads that. `record_decision` trusts the orchestrator's reading of who wrote the message: there is no mapping from Jira accounts to AgentFlow members yet. See [People in the loop](/docs/concepts/people-in-the-loop).

## What is not guarded yet?

- Who may approve in a thread.
- Budgets per case or project (turns per hour, tasks, cost).
- Cancelling only on backward moves: the rules decide, not the platform.
- Hardening against untrusted ticket text beyond marking it untrusted in the prompt.

What is guarded today: undeclared commands, write tasks of read commands, missing `needs`, write tools of a superseded turn, writes not granted in `agent.orchestrator.connections`, and `task_cancel` outside a ticket change turn. Refused calls show on the case as "Refused" messages.

## Why does "runner" appear in YAML and environment variables?

Agents used to be called runners. In YAML an Agent is named with the key `runner`, and environment variables keep names such as `AGENTFLOW_RUNNER_*`. See [Agent CLI](/docs/reference/agent-cli) and [Glossary](/docs/reference/glossary).

## Where do I see why a case is stuck?

Open Home and look at Needs attention, then open the case. See [Cases](/docs/guides/operate/cases) and [Troubleshooting](/docs/resources/troubleshooting).
