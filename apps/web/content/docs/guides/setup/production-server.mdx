title: "Deploy the server for production"
description: "Run AgentFlow on its own domain with Docker Compose: environment, HTTPS reverse proxy, upgrades and backups."
---

[Install the server](/docs/getting-started/install-server) starts AgentFlow in development mode (`pnpm dev`) on one machine. This page runs the same server for a team: built into Docker images on the server, started by one Compose file, behind HTTPS, with backups and a way to upgrade.

## What you deploy

The Compose file is `deploy/compose/docker-compose.prod.yml` (project name `agentflow-prod`). Every published port is bound to `127.0.0.1`: only your reverse proxy reaches them.

| Part | Port | Reached by | Public URL (example) |
|---|---|---|---|
| app (web app) | 3000 | Browsers, through your proxy | `https://agentflow.example.com` |
| api | 3002 | Browsers, Agents (HTTPS and WebSocket), Jira and Azure DevOps webhooks, through your proxy | `https://api.agentflow.example.com` |
| mcp | 3010 | Agents, through your proxy | `https://mcp.agentflow.example.com` |
| rustfs (S3 API) | 9000 | Browsers and Agents, through presigned URLs and your proxy | `https://s3.agentflow.example.com` |
| rustfs console | 9001 | Administrators only, on `127.0.0.1` (use an SSH tunnel) | none |
| postgres | 5432 | The api, mcp and migration job, inside the Compose network. Not published on the host | none |
| local-git | 3300 | The api and Agents, when you use [Local Git](/docs/integrations/local-git). Optional profile `local-git`, off by default | optional |
| mailpit | 8025 (UI), 1025 (SMTP) | Administrators (UI, behind a password) and the api (SMTP). Optional profile `mailpit`, off by default | none |

One-shot jobs: `migrate` (`prisma migrate deploy`) and `storage-init` (buckets and CORS rules) run before the api starts; `bootstrap-admin` creates the first AgentFlow owner once the api is healthy; `local-git-init` (profile `local-git`) creates the Gitea admin and token. All of them use the api image, except `local-git-init`, which uses the Gitea image.

Agents connect outwards to the API and the MCP server, so the machines they run on need no open port. `apps/relay` is not needed: Agents connect to the WebSocket the API process hosts.

## 1. Prerequisites

- A Linux server with Docker Engine and Compose v2.
- At least 8 GB of RAM, or swap. The api and app builds each use up to 4 GB of Node heap (`NODE_OPTIONS=--max-old-space-size=4096` in their Dockerfiles). On a small machine build one image at a time: `build api`, then `build app`, then `build mcp` (with the `afc` alias from step 4).
- About 20 GB of free disk for Docker. A first build of the three images from an empty build cache uses that much; the finished images are about 2.1 GB (api), 450 MB (app) and 700 MB (mcp).
- A reverse proxy that already terminates HTTPS.
- DNS records for the four hosts: app, api, mcp and s3.

## 2. Get the source

```bash
git clone <repository> /opt/agentflow && cd /opt/agentflow
git checkout <release tag>
```

## 3. Environment

```bash
cp deploy/compose/.env.prod.example deploy/compose/.env
chmod 600 deploy/compose/.env
```

Edit `deploy/compose/.env`. [Server environment variables](/docs/reference/server-env) lists every variable; these are the ones to set:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_APP_URL` | The web app origin, `https://agentflow.example.com` |
| `NEXT_PUBLIC_API_URL` | The API origin, `https://api.agentflow.example.com` |
| `NEXT_PUBLIC_WEB_URL` | The marketing and docs site, or the app origin if you do not run one |
| `MCP_SERVER_URL` | `https://mcp.agentflow.example.com` (without `/mcp`) |
| `S3_PUBLIC_ENDPOINT` | Required. `https://s3.agentflow.example.com`, baked into presigned URLs; browsers and Agents must reach it |
| `POSTGRES_PASSWORD` | `openssl rand -hex 32` (URL-safe: it is used inside `DATABASE_URL`) |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | `openssl rand -hex 16` and `openssl rand -hex 32`. They are also the RustFS root credentials |
| `BETTER_AUTH_SECRET` | `openssl rand -base64 32` |
| `ENCRYPTION_KEY` | `openssl rand -base64 32`. Keep it safe: without it stored tokens cannot be read |
| `INTERNAL_API_SECRET` | `openssl rand -hex 32`, shared by the app, api and mcp |
| `AGENTFLOW_RUNNER_JWT_SECRET` | `openssl rand -hex 32`. Required: the api refuses to start without it. At least 32 characters with at least 8 different characters |
| `SMTP_URL`, `EMAIL_FROM` | Your mail server and sender (see [Email](/docs/integrations/email)) |
| `AGENTFLOW_ADMIN_EMAIL`, `AGENTFLOW_ADMIN_PASSWORD` | Required. The first AgentFlow owner, created by the `bootstrap-admin` job. Password: at least 8 characters, `openssl rand -base64 18`. `AGENTFLOW_ADMIN_NAME` is optional (default `Administrator`) |
| `AUTH_ALLOW_SIGN_UP` | Set `false` to make the deployment invite-only. The first owner is created from `AGENTFLOW_ADMIN_*`, so no one needs to sign up first |

Comment out variables you do not use: an empty value (`""`) fails validation. The Compose file sets these itself, so do not set them: `DATABASE_URL`, `S3_ENDPOINT`, `BETTER_AUTH_URL`, `AGENTFLOW_MCP_URL`, `AUTH_API_URL`. The host ports can be changed in `.env`; the `NEXT_PUBLIC_*` values and `MCP_SERVER_URL` must still be the public URLs your reverse proxy serves.

Build time versus runtime. The `NEXT_PUBLIC_*` variables are baked into the app and the api images: after changing one, run `up -d --build`. Every other value is read when the container starts: after changing one, run `up -d`, which recreates the containers that use it. Only the api container receives the whole `.env` file; the app and mcp containers get just the variables the Compose file lists for them.

## 4. Start

Compose reads `.env` from the project directory, which is the directory of the first `-f` file, so `deploy/compose/.env` is picked up for variable substitution wherever you run the command. Define an alias once (add it to your shell profile):

```bash
alias afc='docker compose -f /opt/agentflow/deploy/compose/docker-compose.prod.yml'
```

The rest of this page uses `afc`. Without the alias, write the full command, for example:

```bash
docker compose -f deploy/compose/docker-compose.prod.yml up -d --build
```

Start everything:

```bash
afc up -d --build
```

What happens: Compose builds the api, app and mcp images, starts postgres and rustfs, and waits for both to be healthy. `migrate` applies the database migrations and `storage-init` creates the buckets and the browser CORS rules; both exit when done. Then the api starts (with the `local-git` profile it also waits for `local-git-init`; with the `mailpit` profile, for mailpit to be healthy). `bootstrap-admin` runs once the api is healthy and creates the first owner from `AGENTFLOW_ADMIN_*` (it does nothing when a user already exists). The app starts when the api is healthy and `bootstrap-admin` has completed, so the sign-up page is not served before the owner exists. This gates only the app container: the api accepts `POST /api/auth/sign-up/email` as soon as it is healthy, before `bootstrap-admin` runs, unless `AUTH_ALLOW_SIGN_UP=false` (only emails with a pending invitation can then sign up; the bootstrap job bypasses that check for the first owner). Set `AUTH_ALLOW_SIGN_UP=false` for the first `up` if the api host is reachable by anyone else. mcp starts after the migration job completes and the api has started.

```bash
afc ps -a          # the jobs show "Exited (0)"
afc logs -f api
afc logs bootstrap-admin
```

Run one API process. It hosts the in-process scheduler and the WebSocket every Agent connects to; see [The scheduler](/docs/getting-started/install-server#the-scheduler) to move scheduling elsewhere.

## Accounts

Every account comes from `deploy/compose/.env`. Nothing needs a manual step after `up`.

| Account | Variables | What creates it, and when | How to rotate |
|---|---|---|---|
| Postgres | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Postgres itself, on the first start of an empty `postgres_data` volume only. Later changes to these variables do not change the database | `afc exec postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB> -c "ALTER USER <POSTGRES_USER> PASSWORD '<new>'"`, then update `.env` and run `afc up -d` |
| RustFS | `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | RustFS root credentials, read at every start. They are also the keys the api uses | Change both in `.env`, then `afc up -d` |
| AgentFlow first owner | `AGENTFLOW_ADMIN_EMAIL`, `AGENTFLOW_ADMIN_PASSWORD`, `AGENTFLOW_ADMIN_NAME` | The `bootstrap-admin` job, on every `up`. It creates the owner only when no user exists | Change the password in the app. The `.env` value only takes effect when the owner is created; `AGENTFLOW_ADMIN_PASSWORD` must stay set because Compose requires it on every `up`, and a stale value is harmless after the password is changed in the app. The job never changes the email of an existing user |
| Local Git admin | `LOCAL_GIT_ADMIN_USER`, `LOCAL_GIT_ADMIN_PASSWORD`, `LOCAL_GIT_ADMIN_EMAIL`, `LOCAL_GIT_OWNER` | The `local-git-init` job, on every `up` with the `local-git` profile. It creates the admin, or re-applies only the password to the existing one (a changed `LOCAL_GIT_ADMIN_EMAIL` is ignored for an existing admin; change it in Gitea), and creates the `LOCAL_GIT_OWNER` organization when set | Edit `.env`, then `afc --profile local-git up -d` |
| Local Git token | none (`LOCAL_GIT_TOKEN_FILE` is set by the Compose file) | The same job writes an access token to `/run/local-git/token` on the `local_git_token` volume, which the api mounts read-only. A token that is still valid is kept | Delete the file, then `up -d` issues a new one (command below) |
| Mailpit UI | `MAILPIT_UI_USER`, `MAILPIT_UI_PASSWORD` | Mailpit, at every start with the `mailpit` profile. The password is required | Edit `.env`, then `afc --profile mailpit up -d` |

To rotate the Local Git token:

```bash
afc --profile local-git run --rm --entrypoint rm local-git-init /run/local-git/token
afc --profile local-git up -d
```

## 5. HTTPS reverse proxy

Point each host at its local port:

| Host | Target |
|---|---|
| `agentflow.example.com` | `127.0.0.1:3000` |
| `api.agentflow.example.com` | `127.0.0.1:3002` |
| `mcp.agentflow.example.com` | `127.0.0.1:3010` |
| `s3.agentflow.example.com` | `127.0.0.1:9000` |

The proxy must:

- pass WebSocket upgrades to the API (Agents connect to `/socket.io/` with WebSocket only);
- not buffer the MCP server's streamed responses;
- allow large request bodies on the API and on the s3 host, for attachment uploads.

```nginx title="/etc/nginx/conf.d/agentflow.conf"
# TLS directives (listen 443 ssl, certificates) omitted: add them to each server block.
server {
  server_name agentflow.example.com;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}

server {
  server_name api.agentflow.example.com;
  client_max_body_size 100m;
  location / {
    proxy_pass http://127.0.0.1:3002;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}

server {
  server_name mcp.agentflow.example.com;
  location / {
    proxy_pass http://127.0.0.1:3010;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 3600s;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}

server {
  server_name s3.agentflow.example.com;
  client_max_body_size 100m;
  location / {
    proxy_pass http://127.0.0.1:9000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

With Caddy, which handles certificates and WebSockets by itself, `reverse_proxy 127.0.0.1:3002` is enough for the API, and the MCP host needs `flush_interval -1` inside its `reverse_proxy` block. With Traefik, the published ports are bound to `127.0.0.1` on the host, so a Traefik container cannot reach them through the host IP or `host.docker.internal`. Either run Traefik on the host network and target `127.0.0.1:<port>`, or attach the Traefik container to the `agentflow-prod_default` Compose network and target the service names (`app:3000`, `api:3002`, `mcp:3010`, `rustfs:9000`).

Jira Cloud and Azure DevOps call `PUBLIC_WEBHOOK_BASE_URL` (default: the API origin), so the API host must be reachable from the internet for webhooks. If it cannot be, use poll mode on the connection.

## 6. Check it

1. Open the app URL and sign in with `AGENTFLOW_ADMIN_EMAIL` and `AGENTFLOW_ADMIN_PASSWORD` ([First admin and organization](/docs/getting-started/first-admin)).
2. Upload an attachment to a document: it checks `S3_PUBLIC_ENDPOINT` and the CORS rules.
3. Start an Agent with `AGENTFLOW_API_URL=https://api.agentflow.example.com` ([Install an Agent](/docs/getting-started/install-agent)). It appears online under **Agents** when the WebSocket works.
4. Test a connection and send one webhook (for Jira, change a ticket's status) and check that the workflow starts.

## Upgrade

1. Back up (below).
2. Fetch the new version and rebuild:

   ```bash
   cd /opt/agentflow
   git fetch && git checkout <new tag>
   afc up -d --build
   ```

   The `migrate` job runs the new migrations before the api restarts. Optionally reclaim disk with `docker image prune`.

3. Upgrade the Agents when they are idle: [Agent CLI and environment](/docs/reference/agent-cli). Agents reconnect to the API by themselves after it restarts, and a loop that ends while the API is down is reported when its Agent reconnects.

## Back up and restore

The volumes are `agentflow-prod_postgres_data`, `agentflow-prod_rustfs_data` and `agentflow-prod_local_git_data`, plus `agentflow-prod_local_git_token` (the Local Git token, re-issued by `local-git-init` if lost) and `agentflow-prod_mailpit_data` (caught mail, only with the `mailpit` profile; usually not worth backing up). Back up these together:

| What | How |
|---|---|
| Database | `afc exec -T postgres pg_dump -U postgres -Fc agentflow_ai > agentflow-$(date +%F).dump` (use your `POSTGRES_USER` and `POSTGRES_DB` if you changed them) |
| Files (RustFS) | Stop `rustfs` briefly and archive its volume: `afc stop rustfs`, then `docker run --rm -v agentflow-prod_rustfs_data:/data -v "$PWD":/backup alpine tar czf /backup/rustfs-$(date +%F).tgz -C /data .`, then `afc start rustfs`. Or mirror the buckets with an S3 client |
| Local Git | The `agentflow-prod_local_git_data` volume, the same way, if you use it |
| Secrets | `deploy/compose/.env`. `ENCRYPTION_KEY` must match the database it was backed up with |

Restore the database with the api, mcp and app stopped:

```bash
afc stop api mcp app
afc exec -T postgres pg_restore --clean -U postgres -d agentflow_ai < agentflow-2026-01-01.dump
afc start api mcp app
```

Restore a volume by extracting its archive into an empty volume, then start the services.

## Local Git (optional)

Add `--profile local-git` to every `afc` command (or set `COMPOSE_PROFILES=local-git` in `deploy/compose/.env`). In `.env` set `LOCAL_GIT_ADMIN_PASSWORD` (required with the profile), and optionally `LOCAL_GIT_ADMIN_USER` (default `agentflow`), `LOCAL_GIT_ADMIN_EMAIL` and `LOCAL_GIT_OWNER`. Set `LOCAL_GIT_URL` to the public URL you proxy to `127.0.0.1:3300`; Agents use it too unless you set `LOCAL_GIT_RUNNER_URL`. Then start it:

```bash
afc --profile local-git up -d
```

The `local-git-init` job creates the admin user and an access token, and the api reads the token from `LOCAL_GIT_TOKEN_FILE` (`/run/local-git/token`, set by the Compose file). You do not paste a token into `.env`; `LOCAL_GIT_TOKEN` is only an override. The api reaches Gitea at `http://local-git:3000` (`LOCAL_GIT_SERVER_URL`). See [Accounts](#accounts) for rotation and [Local Git](/docs/integrations/local-git).

## Orchestrator Agent (optional)

An orchestrated workflow needs an automatic Agent for its Orchestrator Agent ([Orchestrator](/docs/guides/setup/orchestrator)). The profile `orchestrator` runs one in this stack: the service `orchestrator-agent`, built from `deploy/runner/Dockerfile`, reaching the api (`http://api:3002`) and the MCP server (`http://mcp:3010/mcp`) inside the Compose network, so it needs no public URL and no published port.

1. After the first `up`, sign in and create an API key with the `write` scope (Settings → API Keys). Its owner owns the Agent; a dedicated bot user is a good owner.
2. In `deploy/compose/.env` set `ORCHESTRATOR_AGENT_API_KEY` (required with the profile) and optionally `ORCHESTRATOR_AGENT_NAME` (default `af-orch`), and add `orchestrator` to `COMPOSE_PROFILES`.
3. Start it:

   ```bash
   afc --profile orchestrator up -d --build orchestrator-agent
   afc logs -f orchestrator-agent
   ```

4. Under **Agents**, the Agent appears online: set its **Model provider**, share it with the organization when workflows run as other users, add it in Project → **Agents**, and name it in the workflow (`agent.runner`).

Its volumes (`agentflow-prod_orchestrator_*`) keep its identity and Claude Code sessions across restarts. The orchestrator's turns need no project toolchain; Agents that build and test code run elsewhere ([Agents](/docs/guides/setup/agents)).

## Mailpit (optional)

Mailpit catches outgoing mail so you can read invitations and password resets without a mail server. Add `--profile mailpit` to the `afc` commands (or `COMPOSE_PROFILES=mailpit`), set `MAILPIT_UI_PASSWORD` (required, no spaces) and optionally `MAILPIT_UI_USER` (default `admin`), and point the api at it with `SMTP_URL=smtp://mailpit:1025`. The UI is on `127.0.0.1:8025` (`MAILPIT_UI_PORT`) behind that login; reach it through an SSH tunnel or your proxy. The SMTP port is published on `127.0.0.1:1025` (`MAILPIT_SMTP_PORT`).

```bash
afc --profile mailpit up -d
```

## Optional features

- **Feature flags without PostHog.** Flags still being rolled out are off without PostHog. Turn them on for the whole deployment with `AGENTFLOW_FEATURE_FLAGS` (runtime, `afc up -d`) and `NEXT_PUBLIC_AGENTFLOW_FEATURE_FLAGS` (build time, `afc up -d --build app`) in `deploy/compose/.env`. Comma-separated keys; `-key` forces one off.
- **Live co-editing.** Presence and inline comment threads in the document editors use Liveblocks, a hosted service. Without `LIVEBLOCKS_SECRET` the editors show the saved version and each edit is published as a new version.

## Security checklist

- [ ] Every published port is bound to `127.0.0.1` (check `afc ps`); Postgres is not published at all.
- [ ] `deploy/compose/.env` is readable only by root or the deploy user (`chmod 600`).
- [ ] RustFS credentials, `POSTGRES_PASSWORD`, `INTERNAL_API_SECRET`, `AGENTFLOW_RUNNER_JWT_SECRET`, `BETTER_AUTH_SECRET` and `ENCRYPTION_KEY` are not the example values.
- [ ] `AUTH_ALLOW_SIGN_UP=false` unless you want open sign-up (the first owner comes from `AGENTFLOW_ADMIN_*`).
- [ ] `AGENTFLOW_ADMIN_PASSWORD`, `LOCAL_GIT_ADMIN_PASSWORD` and `MAILPIT_UI_PASSWORD` are strong and not the example values.
- [ ] Agents run in containers or dedicated VMs, not on the server: they run code agents write from ticket content ([Agents](/docs/guides/setup/agents)).
- [ ] Backups run on a schedule and a restore has been tried once.
