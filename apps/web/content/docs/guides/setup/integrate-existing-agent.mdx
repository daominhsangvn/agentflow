title: "Integrate an existing agent"
description: "Bring a Claude Code agent people already run on their own computer under the orchestrator: what the agent receives and sends, and the prompt text for questions, files, confirmations and results so it never asks people directly."
---

Many teams already have an agent of their own: Claude Code commands, skills and plugins that a developer, BA or QC runs by hand in their project folder. This page turns such an agent into one the Orchestrator Agent can drive. Once integrated, the agent **never asks people at the terminal**: every question, file and result goes through the orchestrator, which talks to people on the ticket (a Jira comment thread, a Teams thread) or on the case page.

You need a [personal Agent](/docs/guides/setup/personal-agent) running in the project folder and an `AGENTFLOW.md` that declares its commands ([Agent capabilities](/docs/guides/setup/agent-capabilities)). This page is about the commands themselves.

## How a task runs

```text
 people (Jira / Teams / case page)
        │  comments, status moves, answers, approvals
        ▼
 Orchestrator Agent  ── task_run ──►  your agent (personal Agent, your project folder)
        ▲                               │ runs your command: /plan-ticket LD-6 ...
        │                               │ writes files into $AGENTFLOW_WORKDIR
        └── result: reply, questions, ──┘ and stops
            files
```

A **task** is one run of one declared command. The agent cannot talk to the orchestrator while it runs and cannot wait for an answer: it writes files and stops. The orchestrator reads them when the run ends, talks to people, and starts the next task, or resumes this one with the answers.

## What the agent receives

| What | Where | Notes |
|---|---|---|
| The command and its arguments | First line of the prompt, e.g. `/plan-ticket LD-6` | Only commands declared in `AGENTFLOW.md` are started |
| The request | The rest of the prompt, written by the orchestrator: what is asked, the context, decisions people made | The spec of this task |
| A footer from AgentFlow | End of the prompt: where to write the answer, which files to leave, which inputs exist, read-only notice | Generated; do not depend on its wording |
| The case | `$AGENTFLOW_WORKDIR/issue.md` | The case (notes, tasks, decisions) as it stood when the case's first task on this Agent started; the request carries what changed since |
| Input files | `$AGENTFLOW_WORKDIR/inputs/<name>` | Files of earlier tasks (a PRD, a plan) or a Confluence page as Markdown: at most 5 files, 400 KB together |
| Answers to its questions | A new prompt in the **same session** (the task is resumed) | The session still has what the agent did and asked |
| A question about its earlier work | A **forked** copy of the session | It answers from what it knew; the original session is unchanged |
| Read-only mode | A task of a `mode: read` command | Edit tools, `git commit` and `git push` are denied; the answer file can still be written |

`$AGENTFLOW_WORKDIR` is set on every AgentFlow run. On a personal Agent it is `<project folder>/.agentflow-ai/runs/<case id>`: one per case, kept across the case's tasks. When it is not set, a person typed the command.

## What the agent sends back

| What | File | Notes |
|---|---|---|
| **The answer** | `$AGENTFLOW_WORKDIR/orchestrator-reply.md` | Read when the run ends, up to 30,000 characters |
| **Questions for people** | `$AGENTFLOW_WORKDIR/questions.json` | Only for a command with `asks: true`. At most 30 questions of 2,000 characters, 10 options of 500 characters each. A question may carry an optional `commentId` |
| **Files for the ticket** | Files in `$AGENTFLOW_WORKDIR` that match the command's `attach` globs, or, when the toolkit writes elsewhere, files of a folder named in `attachRoots` (`features:**/*.md`, with `attachChanged: true` to take only what this run changed) | Collected when the run ends (20 files, 4 MB each, 5 MB in total). The orchestrator attaches them, publishes them to Confluence or hands them to later tasks; people view and download them on the case page |
| **Cannot start** | First line of the answer: `BLOCKED: <what is missing>` | The orchestrator tells people what is missing and who produces it |
| **Code** | The person's own branch, push and pull request | With the computer's credentials. Nobody merges but people |

## What the agent must not do

- **Ask people directly**: no `AskUserQuestion`, no "Proceed? (y/n)", no terminal prompt, no Slack, Teams or Jira comment asking something, unless the command comments the question itself and writes the comment's id as `commentId` in `questions.json`. Nobody is at the terminal, and the orchestrator would not know a question was asked.
  AgentFlow already guards against a command written for the terminal: every run denies `AskUserQuestion`, and the agent is told that wherever its command says to ask the user, wait for a reply or confirm, it writes the questions to `questions.json` and stops (`asks: true`) or decides and notes it (otherwise). A command written to ask in the terminal usually works unchanged; the blocks below make it reliable and keep its questions well written.
- **Report directly**: no comment or attachment on the ticket, even with the person's own Jira MCP server. The orchestrator decides what is posted where.
- **Wait** inside a run, poll, or plan to come back later. Write the questions and stop.
- **Stop or start other work**: cancelling tasks and starting other Agents is the orchestrator's job. Say what should happen next in the answer.

A permission prompt stops a run the same way a question does: allow the tools a command needs in its front matter (`allowed-tools:`) or set `AGENTFLOW_RUNNER_SKIP_PERMISSIONS=true` on the Agent.

## Prompt text, case by case

Each block below goes into a command (`.claude/commands/*.md`) or a skill as a short "AgentFlow mode" section. Keep the hand-typed behaviour for when `$AGENTFLOW_WORKDIR` is not set, so the same command works both ways.

### The agent needs a decision

```markdown
## Questions
When you need a decision you cannot make from the request, the inputs, the
ticket or the code:
- If `$AGENTFLOW_WORKDIR` is set: first do the work that does not depend on
  the answer, then write ALL open questions at once to
  `$AGENTFLOW_WORKDIR/questions.json` and stop. Do not ask in the terminal,
  do not call AskUserQuestion, do not guess.
  Format: [{"id": "q1", "question": "...", "options": ["A", "B"],
  "commentId": "10234"}] (options and commentId optional; give commentId only
  when you commented the question on the ticket yourself, so it is not posted
  again and the reply to that comment is the answer). Also write orchestrator-reply.md: what you did so far
  and that you wait for answers to q1..qN.
- Otherwise ask the user as usual.
```

People read the questions in a Jira comment, away from your terminal:

- **One decision per question, self-contained.** Name the ticket, file and section: *"LD-6 PRD §3.2: does a half-day leave count as 0.5 day in the team calendar total?"*, not *"How should we count this?"*.
- **Options when the choice is closed**, with the one you recommend and why: *"0.5 (recommended: matches payroll) or 1"*.
- **Stable ids** (`q1`, `q2`, …), the same id when a question is asked again.
- **Batch them.** Every stop is a round trip with people.

### The answers come back

```markdown
## Resuming with answers
If this session already asked questions and the new prompt carries answers:
record them where this command keeps decisions (e.g. a "Decisions" section of
PLAN-<KEY>.md), then continue from where you stopped. Do not start over and
do not ask again what is answered. If answers are missing or raise new
questions, ask only those.
```

The resumed prompt can start with the command again (`/plan-ticket LD-6`) followed by the answers. The command must see that it is a continuation (from the session, or from its own files in the work directory) rather than redo its first step.

### Confirmations

```markdown
## No confirmations
In an AgentFlow run never wait for a yes/no. Use the defaults stated here
(overwrite the previous draft, skip optional steps) and say what you chose in
the answer. A risky choice with no safe default becomes a question.
```

A command that already has an `--auto` flag: write it in the command's `args` in `AGENTFLOW.md` (`<KEY> [--auto]`) so the orchestrator passes it.

### Input files

```markdown
## Inputs
Before anything else (no branch, no clone, no skill), check the inputs:
$AGENTFLOW_WORKDIR/inputs/PRD-<KEY>.md in an AgentFlow run, ./PRD-<KEY>.md by
hand. If it is missing, write exactly one line as the first line of
$AGENTFLOW_WORKDIR/orchestrator-reply.md and stop:
BLOCKED: missing PRD-<KEY>.md (needs prd: produced by /ba-requirement analyze <KEY> on BA)
```

Inputs are the versions people approved: do not correct them silently; report doubts in the answer or as questions.

### Files for the ticket

```markdown
## Output
Write the result to $AGENTFLOW_WORKDIR/PLAN-<KEY>.md (this exact name). Do
not attach it to the ticket, comment it or paste it anywhere: AgentFlow
collects it and the orchestrator decides where it goes.
```

Use fixed names `<KIND>-<KEY>.md` that match the command's `attach` globs (`PLAN-*.md`); the orchestrator hands them to later tasks by name and checks `needs` with them. Screenshots and evidence also go under `$AGENTFLOW_WORKDIR` (`evidence-<KEY>/*.png`) with an `attach` glob. Keep a text file a later task needs under 200 KB.

### The answer

```markdown
## Answer
As the last step, always (also when you failed or stopped with questions),
overwrite $AGENTFLOW_WORKDIR/orchestrator-reply.md with at most ~15 lines:
- Status: done | waiting for answers | BLOCKED | failed: <why>
- What you did, with file names and links (branch, pull request URL)
- Choices you made on your own (defaults)
- What should happen next (who reviews, which command runs next)
```

**Always overwrite it.** A personal Agent keeps one work directory for all tasks of a case, so a task that writes no answer would leave the previous task's answer in place.

### Code changes

```markdown
## Git
Work on branch feature/<KEY>-<slug>. Commit, push and open the pull request
with this computer's credentials (gh, tea, glab). Never merge. Put the pull
request URL in the answer. In a read-only task change nothing, commit nothing.
```

When the Agent runs several tasks at once (`AGENTFLOW_RUNNER_PARALLEL=true`), use a git worktree per ticket: never two tickets in one checkout.

### Questions about earlier work

To answer "why does the plan do X?", the orchestrator forks the session that wrote the plan. Nothing to add to the command, but keep the reasoning in the files (a "Decisions" section): a fresh session can then answer when the old one is gone.

## A block for the project's CLAUDE.md

Paste this once into the project's `CLAUDE.md` (or each command), and keep the command-specific parts (inputs, output names) in the commands:

```markdown
## When run by AgentFlow ($AGENTFLOW_WORKDIR is set)
You run unattended; nobody reads this terminal.
- Never ask in the terminal, never call AskUserQuestion, never wait for a
  confirmation. Decide with the command's defaults, or write the open
  questions to $AGENTFLOW_WORKDIR/questions.json
  ([{"id":"q1","question":"...","options":["..."]}]) and stop.
- Never contact people yourself (no Jira, Slack or Teams comments to ask or
  to report). AgentFlow's orchestrator does that.
- Inputs are in $AGENTFLOW_WORKDIR/inputs/. A missing input: the first line
  of the answer is "BLOCKED: missing <file> (<who produces it>)", then stop.
- Leave output files in $AGENTFLOW_WORKDIR under their fixed names; do not
  attach or post them.
- Always finish by overwriting $AGENTFLOW_WORKDIR/orchestrator-reply.md:
  status, what you did, defaults you chose, what comes next.
- When resumed with answers, record them and continue; do not start over.
- Never merge a pull request.
```

## Declare what it does

The orchestrator only sees what `AGENTFLOW.md` declares. For an existing agent, declare each command it should be given, with `asks: true` on every one that may write `questions.json` (a command without it is told not to ask and to pick a default):

```markdown
---
runner: Dev (LeaveDesk)
commands:
  - name: /plan-ticket
    args: <KEY> [--auto]
    description: Plan a ticket from its approved PRD
    mode: write
    produces: plan
    needs: [prd]
    asks: true
    attach: ["PLAN-*.md"]
  - name: /explain-code
    args: <question>
    description: Answer a question about the code; changes nothing
    mode: read
    produces: answer
---

# Dev (LeaveDesk)

## /plan-ticket
Reads inputs/PRD-<KEY>.md and writes PLAN-<KEY>.md. Asks when the PRD leaves
a behaviour open. Resume it with the answers; fork it to ask about the plan.
```

Every field: [Agent capabilities](/docs/guides/setup/agent-capabilities). How the orchestrator posts the questions and resumes the task: [Questions and answers](/docs/guides/recipes/questions-and-answers).

## Checklist

1. The personal Agent is set up for the project and online in **Agents**, with the Claude Code version AgentFlow pins.
2. `AGENTFLOW.md` is in the project folder, and Project → **Agents** → **Commands** shows its commands without warnings.
3. Every declared command checks its inputs (`BLOCKED`), uses fixed output names, asks through `questions.json`, never waits for a confirmation and always overwrites the answer file.
4. Every command allows the tools it needs (`allowed-tools:`), or the Agent skips permission prompts.
5. Run each command by hand with `AGENTFLOW_WORKDIR=/tmp/af-test` set: it must finish without any prompt and leave its answer (and questions) there.
6. Take one ticket through the whole flow with the orchestrator, with one question answered in the Jira thread.
