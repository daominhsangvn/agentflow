AgentFlow1

The idea

AI agents do the work. People govern it.

People

Keep working in Jira

Move the ticket, answer questions in comments, review on Confluence, merge pull requests.

Orchestrator Agent

Decides the next step

Reads the workflow’s rules and the ticket’s case, starts the right agent, answers in the right thread.

Agents

Do the work

BA writes the PRD, Dev plans and implements, QC designs and runs the tests.

  • Agents ask, people answer. Agents open pull requests, people merge.
  • Documents live on Confluence; people may edit them, and the next version keeps their edits.
  • The process is written in plain language by the admin, not in code.

The agents

Each agent declares what it can do in AGENTFLOW.md

AgentRunsDeclared commands
BA AgentAutomatic, toolkit leavedesk-knowledge /ba-requirement produces the PRD, asks questions · /ba-archive needs the PRD, pushes · /leavedesk-research read
Dev AgentPersonal: the developer’s machine and credentials /writing-plans needs the PRD, leaves the plan · /executing-plans needs the approved plan, opens its own PR · /systematic-debugging read
QC AgentAutomatic, toolkit leavedesk-qa, Playwright /qa-test needs the PRD, leaves the test plan · /qa-run needs the test plan, tests the Dev branch · /qa-review read

Each command declares its mode (read or write), what it needs and produces, the files it leaves and whether it pushes. AgentFlow refuses a command that is not declared, a write from a read command, or a missing input.

Rules · the admin

What to do

Roles and process by status. Work belongs to its status. Coming back to a status starts nothing. Answer each comment in its own thread.

The case study

LD-6 · “As a manager I want a calendar of who in my team is off”

  • PRD: 8 questions, answered in parts; a person’s edit on Confluence kept: PRD v1 → v4 on the same page.
  • Planning: three agents in parallel from the PRD page: archive PR, implementation plan, test plan (v2 after a QC question).
  • Implement: the Dev Agent on the developer’s machine, TDD, opens PR #6.
  • Testing: round 1 fails 32/33 (defect D-1), back to Implement, fix, round 2 passes 33/33.
  • Review → Done: people review three pull requests, ask in Jira, merge.
Along the way

Four comments within seconds, a status changed by mistake, a ticket sent back to a status whose work was done: what people really do.

Throughout

People moved the ticket, answered, edited pages and merged. Every task, page version, reply and pull request came from the Orchestrator Agent’s decisions.

CASE 4

Testing: fail → fix → pass

32/33, back to Implement, fix D-1, 33/33.

CASE 5

Review → Done

Questions answered by reading tasks; people merge; case closed.

CASE 6

Comments in one window

Four comments, one turn, each answer in its own thread.

CASE 7

Accidental status flip

Implement → Planning → Testing in seconds: only the final status counts.

CASE 8

Coming back to a status

Report what exists, start nothing, wait for an instruction.

Cases 1–5 are the ticket’s life. Cases 6–8 are what people do. In LikeC4, every decision of the Orchestrator Agent carries a “Why this step” note quoting the rule behind it.
